rrffmpeg

A remote FFmpeg wrapper in Rust. It stands in for ffmpeg and sends each job to the machine that has the GPU, over SSH or through the rrffmpeg-agent daemon. It never touches video quality, remuxing or encoding. Only dispatch.

One dependency-free static binary, no daemon on the client, no database.

Why it exists

The maintained options are weak. The Python rffmpeg commits to SQLite with an fsync between "decide to run" and "run ffmpeg", marks a GPU host bad forever after one SSH error, and leaves orphan rows on SIGKILL. rffmpeg-go is archived. dffmpeg has the right architecture but is beta.

Meanwhile the layout "small GPU node plus separate storage host" is common in home labs: an Intel N100 with QuickSync on one side, the NAS on the other. The people running it have no maintained dispatcher.

  • 64 msdispatch with the journal on tmpfs
  • 2 to 4 sthe same dispatch when the fsync sits on the hot path
  • 1.54xrealtime, 4K HEVC HDR with tonemap_opencl
  • 2.67xrealtime, 1080p SDR

Measured against rffmpeg

Same box, same ffmpeg 8.0.1, same SSH server, one session. Ffmpeg is replaced by /bin/true to isolate the dispatch, then the real ffmpeg -version runs. 60 samples per row, warm SSH connection.

DispatcherDispatch only, p50ffmpeg -version, p50p99
local ffmpeg0.35 ms24.18 ms25.43 ms
rffmpeg, state on nvme65.78 ms117.26 ms120.90 ms
rrffmpeg, SSH7.23 ms33.40 ms37.63 ms
rrffmpeg, agent1.56 ms27.77 ms30.37 ms

rffmpeg spends about 55 ms before any transport: Python start, its imports and four SQLite commits. Its per-job health probe then opens a second SSH connection and starts ffmpeg twice, which is why a 24 ms probe becomes 117 ms.

On the production pair, the same probe sent from the Jellyfin host to its GPU worker takes 206.4 ms p50 through rffmpeg and 52.4 ms through rrffmpeg, against 30.1 ms locally. The dispatch alone is 155.8 ms against 32.8 ms, and rffmpeg runs the worker ffmpeg twice per job: once for its health probe, once for the job. With rrffmpeg's journal on the host's own disk instead of tmpfs, the dispatch rises by 39 ms.

The method, the raw runs and the rffmpeg config are in compare-rffmpeg.md.

Features

  • Exact argument passthrough. file: prefixes, startup probes (-version, -encoders), stdin write from Jellyfin, stderr stats on stderr. Nothing is rewritten.
  • One binary, two names. Symlink it as ffmpeg and ffprobe, because Jellyfin derives ffprobe from the ffmpeg path.
  • Bookkeeping off the hot path. An append-only journal with a background flusher. The transcode starts at once.
  • What the job did, in the journal. Each finished job records the fps and speed ffmpeg reported, the source and output codec and size, whether the source was HDR, and whether each stream was copied or re-encoded, so a direct stream and a transcode read apart. The fps and speed are the highest average the job reached, so a slow start does not pass for a slow machine. rrffmpeg-stats prints them as percentiles and tables, and Alloy ships the same lines to Loki.
  • In-process janitor. Retests unhealthy hosts, reaps orphans, requeues. No cron watchdog.
  • Cross-process concurrency cap. One lock file per worker slot, freed by the kernel when the process dies. The "host down" verdict is shared with an expiry, so one failure does not poison the others.
  • Capability-aware placement. Workers advertise vaapi, vaapi_hevc10, vaapi_tonemap, qsv, nvenc and their slot count. A job that needs 10-bit HEVC waits for a worker that encodes it, instead of failing on one that only lists the encoder. The scheduler matches instead of applying a global weight.
  • Path mapping in both directions. Longest-prefix mapping for input and output, so the worker can mount media and the HLS tmpfs at another root.
  • Two transports, one per host. SSH needs nothing installed on the worker. Or run the small rrffmpeg-agent daemon and skip the per-job handshake and probe. The scheduler does not know which one a host uses.
  • Priority, then weight, across processes. A waiting job publishes a ticket and takes a slot only when no better ticket waits: a probe before a transcode, then the client with the smaller share of recent starts per client_weight. Two clients share a busy worker in the ratio of their weights, and a client alone still takes every slot.
  • No silent local fallback. fallback_local = false makes an ffmpeg job fail with exit 1 instead of encoding on a client with no GPU. A local ffprobe still runs. Per-host ssh_args carry the key, and per-host env replaces the worker wrapper script.

Install

Every v* tag publishes static Linux builds for x86_64 and aarch64 on the releases page, with a checksum next to each tarball. A static build needs no toolchain and no matching glibc on the Jellyfin host.

curl -fsSL https://raw.githubusercontent.com/vasilvestre/rrffmpeg/main/scripts/install.sh | sudo sh
rrffmpeg --version

The script checks the checksum, installs rrffmpeg and rrffmpeg-stats, links ffmpeg and ffprobe, and keeps the previous binary as rrffmpeg.prev for a rollback. Run the same command to update. On a worker that uses the agent transport, add -s -- --agent to install the daemon only.

No root is required. sudo is there only to write the default /usr/local/bin. Set PREFIX to install into a directory you own, then point Jellyfin at $PREFIX/ffmpeg:

curl -fsSL https://raw.githubusercontent.com/vasilvestre/rrffmpeg/main/scripts/install.sh | PREFIX=$HOME/.local/bin sh

The user that runs Jellyfin must be able to read and execute that path. Many distros set ProtectHome=true on the Jellyfin unit, which hides every home directory, so a shared path such as /opt/rrffmpeg/bin is the safer choice.

--version answers only under the rrffmpeg name, so the ffmpeg symlink keeps forwarding -version to the real ffmpeg.

The same tarball carries rrffmpeg-agent for the worker. Copy it there only if you want the agent transport instead of SSH. It speaks TLS, and the client trusts exactly one certificate: the daemon's own.

It also carries rrffmpeg-stats. Install it on the client and it reads the journal back: percentiles of dispatch cost and job duration, per host, exit codes, open jobs, orphan events. --json prints one object for a log collector.

rrffmpeg-stats --dir ~/.local/state/rrffmpeg

Generate the certificate on the worker. List every name and address a client uses to reach it:

rrffmpeg-agent --init ~/.config/rrffmpeg --san worker --san 10.8.0.2

That writes cert.pem and key.pem, the key mode 0600. Start the daemon with a long random token:

RRFFMPEG_AGENT_TOKEN=change-me rrffmpeg-agent \
    --listen 10.8.0.2:9876 \
    --cert ~/.config/rrffmpeg/cert.pem \
    --key ~/.config/rrffmpeg/key.pem

Copy cert.pem to the client over a channel you already trust: it is the only thing between the client and an impostor. Then set agent_token and agent_cert on the client, and agent_addr on the host. Hosts without agent_addr keep using SSH, so one config can mix both.

The certificate proves the daemon to the client. The token proves the client to the daemon, and a stolen token still works from any host that reaches the address, so keep the listener on a private network until mTLS exists.

Point Jellyfin at /usr/local/bin/ffmpeg, or at $PREFIX/ffmpeg when you used a custom prefix. Without a config file the binary runs the local ffmpeg and does nothing else, so the install is safe before the worker exists.

Configuration

The file is read from $RRFFMPEG_CONFIG, then $XDG_CONFIG_HOME/rffmpeg/config.toml, then ~/.config/rffmpeg/config.toml. Missing keys take the defaults below. RRFFMPEG_LOG sets the log level: off, error, warn, info or debug, default warn. Logs go to stderr; debug adds the relayed byte count per job on the agent path.

Choosing a transport

SSH costs one process and one key exchange per job, and needs nothing on the worker. Pick it when the worker cannot accept an inbound connection, cannot keep a daemon running, or must not run arbitrary argv. Pick the agent when the client sends bursts of short calls (Jellyfin startup probes, seeks, ffprobe), when the link has real latency, or when a killed client must not leave a transcode running on the worker. Measure first: time ffprobe -version through the dispatcher. Under 50 ms at p99, SSH is enough.

Measured on one loopback box with ffmpeg 8.0.1: a full dispatch at p99 is 32.95 ms, of which ffmpeg is 27.8 ms, the dispatcher 3.8 ms and the TLS transport 0.4 ms. Over SSH with connection persistence the same dispatch is 37.94 ms p50 and 46.94 ms p99; with persistence off it is 155.60 ms p50. A journal of 3000 records adds 1.3 ms to every dispatch, so keep state_dir on a fast filesystem. The harness and the raw runs live in docs/latency.md.

Put state_dir on tmpfs when the disk is slow, because every invocation replays the journal before it dispatches. After queue_wait_secs without a free slot the job runs locally unless fallback_local = false, which refuses an ffmpeg job with exit 1 and still allows a local ffprobe. A client without a GPU sets the switch and watches the no worker slot log line.

Path maps

Each entry rewrites a client prefix to a worker prefix, longest match first. The host probe stats every to root, so a dead mount marks the host down instead of failing each job with ENOENT. Map input and output separately: media and the HLS tmpfs are usually two different mounts.

Example

state_dir = "/home/alice/.local/state/rrffmpeg"
down_ttl_secs = 60

# Every client sharing this state_dir must use a different name.
# client_name = "client"
# Share of a busy worker, 1 to 1000. Only counts while two clients wait.
# client_weight = 100

# Only needed when a host sets agent_addr.
# agent_token = "change-me"
# agent_cert = "/home/alice/.config/rrffmpeg/worker-cert.pem"

[[hosts]]
name = "worker"
concurrency = 2
capabilities = ["vaapi", "vaapi_hevc10"]

# Uncomment to use the agent instead of SSH for this host.
# agent_addr = "worker:9876"

# Input: media mounted at a different root on the worker.
[[hosts.paths]]
from = "/home/alice"
to = "/home/bob/media"

# Output: HLS segments on the client tmpfs, through a second mount.
[[hosts.paths]]
from = "/dev/shm/jellyfin-transcode"
to = "/home/bob/transcode"

Status

Working today: passthrough verified against real ffmpeg 8.0.1, one worker over SSH, an agent transport, path mapping both ways, journal plus janitor, per-host cap, capability match, priority and per-client weight across processes, and a replay test driven by invocations recorded from a real Jellyfin server. A job that fails before the worker starts ffmpeg is retried once on another host (ADR 0013). A job whose client dies is not replayed: nobody is left to read its output.

Design choices and their costs are written down in the decision records.
