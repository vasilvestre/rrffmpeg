# 0.11.0

Release date: 2026-11-19

A client with a GPU had no way to use it without giving up on routing. Local
mode handled every job and ignored capabilities. Worker mode sent every job
over the network. A `[[hosts]]` entry with `local = true` fixes that: the
client's own GPU becomes a host the scheduler can choose, next to the workers.

It changes no config key and no on-disk format. A config without a local host
behaves exactly as before.

## What changed

- `local = true` on a host runs its jobs on the client, through the same
  scheduler, journal, slot locks and queue as any other host. The scheduler
  reads its `capabilities`, so an AV1 job skips a UHD 630 that cannot encode it
  and lands on the N100, while H.264 stays local and out of the network.
- The transport is `transport::Local`. It spawns `local_ffmpeg` with
  `local_env` then `[hosts.env]`, pipes the tapped stream so progress and
  `stderr_as_stdout` behave as they do over ssh, writes a pid file before the
  job can be forgotten, and reports the exit code or 128 plus the signal.
- The child asks the kernel for `SIGTERM` when the dispatcher dies. Jellyfin
  cancels a transcode by killing the process it started, which is the
  dispatcher here; without that, ffmpeg would keep encoding into the same
  output directory and hold the GPU.
- The config refuses what the field would otherwise ignore: `local` with
  `agent_addr`, `paths`, `ffmpeg_bin`, `ffprobe_bin` or `ssh_args`, and a second
  local host, because slots are exclusive per host name.
- `local_ffmpeg` pointing at this program is refused, by path, by hardlink or
  through `PATH`, since every job would fork a copy of the dispatcher.
- `rrffmpeg capabilities <name>` probes a local host in place and never opens
  ssh. `rrffmpeg jellyfin` counts a local host as covering
  `TranscodingTempPath`, because the client writes to its own tmpfs.
- Cost over a direct exec: 0.5 ms. The one structural cost is fork instead of
  exec. Numbers and method in ADR 0029 and `docs/latency.md`.

## What an operator sees

```bash
rrffmpeg capabilities uhd630
```

The token list of the client's own GPU, proved by the one-frame probe, ready to
paste into the host entry.

## Upgrading

Nothing to change unless you want the client's GPU to take part. Then declare
it:

```toml
[[hosts]]
name = "uhd630"
local = true
capabilities = ["vaapi", "vaapi_hevc", "vaapi_hevc10", "vaapi_tonemap"]
```

Keep `local_ffmpeg` and `local_ffprobe` pointing at the real ffmpeg, not at the
`rrffmpeg` symlink.

```bash
rrffmpeg --version
```

Expect `rrffmpeg 0.11.0`.

Next:

```bash
curl -fsSL https://github.com/vasilvestre/rrffmpeg/releases/download/v0.11.0/rrffmpeg-x86_64-unknown-linux-musl.tar.gz \

sudo install -m755 /tmp/rrffmpeg-x86_64-unknown-linux-musl/rrffmpeg /usr/local/bin/ffmpeg
sudo ln -sf /usr/local/bin/ffmpeg /usr/local/bin/rrffmpeg
sudo ln -sf /usr/local/bin/ffmpeg /usr/local/bin/ffprobe
rrffmpeg capabilities uhd630
```
