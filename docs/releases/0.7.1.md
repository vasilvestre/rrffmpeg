# 0.7.1

Release date: 2026-11-17

The fps and speed in the journal are now the real throughput. Two defects in
the parser from 0.7.0 made them read low: ffmpeg's padding hid the value, and
the last line of a job is a running average dragged down by the start.

## Fixes

- The parser reads `fps= 85` and `speed=   5x`, padded by ffmpeg to a fixed
  width. It used to split the line on spaces, miss the value and keep whatever
  it had read earlier.
- `fps` and `speed` are now the highest running average the job reached, not
  the last line. ffmpeg averages both since the start, so a slow first second
  or a stall at the end reported far below the rate the player showed live.
  See [ADR 0023](../adr/0023-the-sample-is-a-peak-not-a-tail.md).

Measured on a 1080p source with the arguments Jellyfin sends: 0.7.0 recorded
`fps: 5.4, speed: 2.12` for a job whose player read 5.76x. 0.7.1 records the
peak, and the same job now reads about 5x.

The bitrate still takes the last value, because it is a moment and not a
running total.

## Upgrading

```bash
rrffmpeg --version
```

Expect `rrffmpeg 0.7.1`. Nothing to change in the configuration.

Lines written by 0.7.0 stay low; compare a dashboard window that starts after
the upgrade.

Next:

```bash
curl -fsSL https://github.com/vasilvestre/rrffmpeg/releases/download/v0.7.1/rrffmpeg-x86_64-unknown-linux-musl.tar.gz \
  | tar -xz -C /tmp
sudo install -m755 /tmp/rrffmpeg-x86_64-unknown-linux-musl/rrffmpeg /usr/local/bin/ffmpeg
sudo ln -sf /usr/local/bin/ffmpeg /usr/local/bin/rrffmpeg
sudo ln -sf /usr/local/bin/ffmpeg /usr/local/bin/ffprobe
rrffmpeg-stats --dir ~/.local/state/rrffmpeg | head -5
```
