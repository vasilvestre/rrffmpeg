# 0.8.2

Release date: 2026-11-18

This completes the journal identity fix from 0.8.1. That release reserved a
block of sequence numbers per process, but replaying the journal still moved
the writer to the highest number on disk, which belonged to another process.
Two processes that replayed the same tail kept writing the same number.

It changes no config key and no on-disk record format.

## What changed

- `replay()` no longer writes the sequence counter. Reading the journal for
  the janitor cannot move this process into another process's block.
  Duplicates from a 0.8.0 journal are still dropped once, by a set of seen
  numbers, and records from a lower block written later are no longer
  skipped.
- A process that fills its block of 1024 numbers reserves the next one under
  the same lock. A long-lived process cannot run into the next block.
- `rrffmpeg-stats` keeps the `orphan_finish` and `orphan_reaped` counters
  added in 0.8.1.
- See [ADR 0026](../adr/0026-a-block-is-exclusive-and-replay-never-moves-the-writer.md).
  0.8.1's [ADR 0025](../adr/0025-sequence-numbers-are-reserved-per-process.md)
  still explains why sequence numbers are reserved per process.

Measured on the development host: 20 concurrent probes, 10 runs, 40 records
and 40 distinct `seq` values every run. The 0.8.1 binary gave 33 to 39
distinct values on the same test. Appending costs 1.26 us before and 1.44 us
after over 2000 appends, including one block renewal. Opening the journal is
unchanged.

## What an operator sees on an old journal

Neither 0.8.0 nor 0.8.1 journals can be repaired. On a journal written by
0.8.1 you may see:

- `orphan_finish` and `orphan_reaped` above zero. The 0.8.1 release note said
  they stay at zero. That was wrong: the lines survive on disk and the new
  counters expose them. Correcting it here.
- `open` too high for jobs whose `finished` line shares a `seq` with another
  event. Those jobs stay open until the records rotate out or you delete the
  journal.
- `records` lower than the line count, because the reader keeps one record
  per `seq`.

To tell new records from old, compare the highest `seq` with the value printed
before the upgrade. On records written after the upgrade, the line count
equals the distinct `seq` count, and new `seq` values are above any value the
old journal reached. To clear a phantom `open` count, stop transcodes and
move the journal aside:

```bash
mv /dev/shm/rrffmpeg-rrj/journal /dev/shm/rrffmpeg-rrj/journal.old
mv /dev/shm/rrffmpeg-rrj/journal.seq /dev/shm/rrffmpeg-rrj/journal.seq.old
```

The old files keep the history for inspection; new processes start at
`seq` 1.

## Upgrading

```bash
rrffmpeg --version
```

Expect `rrffmpeg 0.8.2`. Then read the journal:

```bash
rrffmpeg-stats
```

On a live client, run a transcode and a few probes at once, then compare:

```bash
wc -l /dev/shm/rrffmpeg-rrj/journal
grep -o '"seq":[0-9]*' /dev/shm/rrffmpeg-rrj/journal | sort -u | wc -l
```

The two numbers must match, and `open` must match the number of jobs
actually running.

Next:

```bash
curl -fsSL https://github.com/vasilvestre/rrffmpeg/releases/download/v0.8.2/rrffmpeg-x86_64-unknown-linux-musl.tar.gz \
  | tar -xz -C /tmp
sudo install -m755 /tmp/rrffmpeg-x86_64-unknown-linux-musl/rrffmpeg /usr/local/bin/ffmpeg
sudo ln -sf /usr/local/bin/ffmpeg /usr/local/bin/rrffmpeg
sudo ln -sf /usr/local/bin/ffmpeg /usr/local/bin/ffprobe
rrffmpeg-stats
```
