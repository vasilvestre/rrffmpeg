# 0.7.0

Release date: 2026-11-17

Each finished job now records what the worker's ffmpeg reported about it, so a
playback complaint becomes a number in the journal instead of a guess. No
config key changed: a v0.6.0 `config.toml` works untouched.

## Additions

- The journal's `finished` line carries a progress sample: `fps`, `speed` (times
  realtime), `kbps`, the source size, codec and HDR transfer function, the
  output size and codec, and one verdict per stream, `video`, `audio` and
  `subtitle`, each `copy` or `encode`. A video `copy` is a direct stream; an
  `encode` is a transcode. The verdicts come from ffmpeg's own stream mapping,
  not from the arguments, so a burned-in subtitle or a `-filter_complex` graph
  reads correctly. ADR 0022.
- The `finished` line carries `host` and `dur_us`: which worker ran the job, and
  how long the transport call lasted. The host repeats the one on `started` so a
  dashboard counts failures per worker without joining two lines.
- The `started` line carries `program` (`ffmpeg` or `ffprobe`) and `in_flight`,
  the jobs already running on that worker when this one started, itself
  included.
- `rrffmpeg-stats` prints `speed` (p50, p05, min), `fps` (p50), a `content`
  tally (`2160p hevc hdr`, `1080p h264`) and a `work` tally (`video encode`,
  `audio copy`). `--json` adds `speed_x1000`, `fps_x10`, `content` and `work`.

## Changes

- The SSH transport reads the job's stdout and stderr through pipes instead of
  handing them to Jellyfin with `inherit`, because that is the only way to see
  ffmpeg's stats lines. The bytes, the order and the exit code are unchanged.
- One finished line is about 120 bytes larger for a transcoded job, so the
  8 MiB journal rotates somewhat sooner.

## Upgrading

```bash
rrffmpeg --version   # must print rrffmpeg 0.7.0
```

Then run one transcode and read it back:

```bash
rrffmpeg-stats --dir ~/.local/state/rrffmpeg
```

A job started with `-loglevel error` or `-nostats` records no sample, which is
the normal case for probes and trickplay. The site dashboard reads the same
lines through Alloy and Loki; the panels stay empty until a job runs on the new
binary.

Next: check that the journal has one `finished` line per job with a `speed`
field, then watch the playback speed panel for a week.
