# 0.14.0

Release date: 2026-11-21

The pool cap was a number an operator guessed. `concurrency = 2` is right for
one GPU and wrong for the next, and nothing said when the guess went stale. The
journal already held the answer: every finished job records the speed ffmpeg
reported, the content it worked on, and how many jobs were in flight beside it.
This release reads that back and sizes the pools from it. ADR 0033.

## Breaking change

- An absent `concurrency` on a host with `local = true` no longer means 1. The
  cap is sized from that host's own journal when the process starts. Write
  `concurrency = 1` to keep the old number.
- `concurrency = 0`, `light_concurrency = 0` and `"unlimited"` are a config
  error, with the reason in the message: an unlimited pool admits jobs the GPU
  cannot serve, and the bill lands on a live viewer's stream.

## What changed

- `concurrency` and `light_concurrency` take an integer or `"auto"`. Absent
  means `"auto"`. On a host without `local = true` an absent `concurrency`
  still means 1, with one warning line at startup: sizing a remote host from
  this machine's history would export a guess across the network.
- The heavy cap is the 5th percentile of the solo speeds of the class being
  admitted: the last 200 finished transcodes of that host, longer than 60 s,
  grouped by source codec, height, output codec and tonemap. A sample taken
  beside a neighbour is scaled to `speed * in_flight`. The cap is
  `clamp(floor(solo_p05 / 1.3), 1, min(4, cpus / 2))`. The 1.3 is the headroom
  that leaves one job for the rest of the box, measured on the production
  client: one 1080p HEVC stream at 1.43x, two at about 0.7x each.
- Hysteresis comes from the same tail and needs no file: the last 10 finishes
  of the class raise the cap by 1 when all reached 1.3x or better, the last 3
  lower it by 1 when all came in under 1.0x. Two processes that read the same
  tail compute the same cap, and nothing ratchets.
- A class with no sample gets cap 1 and one log line naming the class.
- The light cap under `"auto"` is `min(4, max(2, cpus / 2))`, fixed: a light job
  lasts seconds and is cheaper than the queue it would wait in.
- Parked jobs. The local transport samples `/proc/<pid>/stat` every 30 s for the
  child it spawned. A job that used under 1% of one CPU for 60 s while its
  output stopped growing is parked: Jellyfin paused the stream, and ffmpeg is
  waiting on stdin. A parked job keeps its slot file but stops counting toward
  the cap, and one spare admission is allowed per parked job, up to the
  ceiling. The next CPU use or output growth resumes it, with no new slot. This
  costs one thread per local job and one `/proc` read every 30 s.
- The journal gains `sized`, `parked` and `resumed`, all with defaults, so an
  older journal still replays. `sized` is an audit line: it records the cap and
  the numbers behind it, and nothing reads it back.
- `rrffmpeg-stats` prints one `size` line per host and class with the current
  cap, the sample count and the p05, and a `parked` line with the count and the
  longest pause. `--json` gains `sizes` and `parked_us` per job.

## Upgrading

Nothing to run. Explicit numbers keep working, and a host that relied on the
old absent-key default on a local machine now sizes itself.

```bash
cargo install --path . --locked
rrffmpeg-stats --dir ~/.local/state/rrffmpeg
```
